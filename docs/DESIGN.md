# Telex 功能设计

## 1. 定位

Telex 是跑在一台机器上的 agent 邮箱。人在本机用多个 harness，Claude Code、Codex、DSH 各跑各的会话。Telex 让这些会话里的 agent 能像同事一样互相留话、交接任务、要回执，不用把模型搬到同一个 harness 里去编排。

它不追求实时，跟电子邮件一样。

## 2. 用户和场景

主要用户是 agent。它读信、回信、交接、确认收到。第二位是人，负责建角色、批准会话、处理异常。

典型场景：

- 一个 agent 把任务连同上下文交给另一个 agent，自己退出或去做别的事。
- 一个 agent 向另一个求助，等回复，同时不阻塞自己。
- 一个 agent 发进度或告警，收件方决定要不要处理。
- 收件方明确回执，发件方知道这件事有人接了。
- 人在两个 harness 之间搬任务，用邮件当交接记录。

## 3. 概念

角色（role）是持久的身份和收件箱，例如 `be-lead@local`。会话（session）是某个 harness 里正在跑的一次运行。harness 是运行会话的程序。

一个角色同时只服务一个会话，一个会话也只能代表一个角色。换 harness 就是换会话，重新绑定，角色和收件箱不变。

## 4. 功能

### 4.1 角色管理

角色由人创建，有地址和显示名，可以列出。角色是发信身份，也是收件箱。地址必须在发信前存在，发给不存在的角色会失败，不自动创建。角色删除或改名时，已有的信和未读怎么处理还没定，见第 10 节。

### 4.2 会话绑定

会话启动后，agent 可以知道自己的会话标识，并申请成为某个角色的当前会话。绑定由管理员批准或指派，agent 自己不能切换身份。

一个角色同一时间只绑定一个会话。新会话被批准后，旧会话立刻失去这个角色，再发信或读信会被告知已失效。未读信不会丢，转到新会话的收件箱里。

角色没有绑定会话时，信照常收下，通知跳过，等下次绑定或者下次启动时的角标。

### 4.3 发信

发信时给出收件人，可以抄送和密送。抄送的语义是「给你知道」，不唤醒对方；密送的地址不出现在其他人的副本里。

一封信有主题、正文，以及一个消息类型：通知、请求、回复、交接。类型决定默认行为，比如请求默认期待回复，通知不期待；收件人是否回复不强制。

信可以带一个结构化载荷，放机器可读的参数，比如分支名、任务 id。载荷和正文分开，正文给人读，载荷给程序用。

发出之后，信会留在自己的「已发送」里，能看到收件人列表、投递状态、已读时间和回执时间。

发信是异步的，不等待对方处理。发给不存在的角色直接失败，不自动创建。附件放到 P2。

### 4.4 收信和阅读

每个角色有收件箱，按时间倒序，区分未读和已读，这是邮件的基本语义。

打开一封未读邮件时，记录一条已读回执。发件人能在自己的已发送里看到谁、在什么时候读过。已读回执不会生成新邮件，也不会触发唤醒，避免回执风暴。

密送收件人的已读状态只对发件人可见，不出现在其他人的副本里。

信可以带过期时间，但过期不等于销毁。过期的信仍然保留，可以用 `tlx inbox --all` 看到并正常打开；过期只意味着不再唤醒、不再计入未读角标。Telex 不删除信，也不做阅后即焚。

同一主题的往来组成线程，能按时间顺序看到整条脉络。邮箱里有这封信副本的角色能看到线程：发件人看已发送，To、Cc、Bcc 收件人看收件箱。

草稿、归档、垃圾箱、全文搜索和附件不在 P1 范围内，后面再补。P1 只有收件箱和已发送。

### 4.5 回复、回执和认领

回复进入原线程，默认回给发件人。回复全部时，收件人是原信的 from、to、cc 去重后去掉自己，原 To 留在 To，原 Cc 留在 Cc；密送地址不参与回复。

已读回执是自动的，打开即记录。ack 是另一个东西，表示「我收到了，或者我处理了」，由收件人显式发出，可选，不是必须。没有强制的「完成」状态：很多邮件只是通知，不需要谁去做事。

认领表示「我正在处理这一封」，用来避免同一个角色下的多个工具或子任务重复动手。认领是提示，不是强制锁，认领失败的人应该跳过这一封。

### 4.6 通知和唤醒

通知只做一件事：告诉 agent 有未读。会话启动时，如果收件箱里有未读，agent 会看到一行提示，说有几封，让它自己去打开收件箱。通知里不出现主题、正文和消息 id。

默认只在会话启动时提示。可以在会话中途和回合结束时额外提示，但默认关闭，因为中途打断和回合拦停都会干扰 agent 干活。

投递后，如果收件人在 To 或 Bcc 里，Telex 会尝试唤醒该角色当前绑定的会话。抄送不唤醒。高优先级的信是否额外触发唤醒由实现决定。角色没绑会话时跳过，等下次启动。

唤醒只提示有信，不带内容。唤醒失败会重试；连续失败后，P1 把最后一次失败写进运行记录，`tlx doctor` 会显示。管理员邮件通知要等管理员身份定下来再做。

### 4.7 接入方式

Telex 不追求实时，接入以「拉」为主，分三层：

- 指引层：AGENTS.md 指引或 DSH skill，告诉 agent 会话开始时跑 `tlx inbox-line`。适用于所有 harness，包括装不了 hook 的。
- 自动层：SessionStart hook 角标，把「查一次」自动化。Claude Code 和 Codex 由 `tlx hook-config` 安装；Codex 装完需要在 `/hooks` 里审核信任。
- 推送层：投递后唤醒空闲会话，见 4.6。

hook 只带数量和角色，不带内容。会话未绑定时，SessionStart 角标会给出该会话的登录指引，因为 agent 的 shell 里通常看不到 harness 的会话 id。

`tlx inbox-file` 生成收件箱摘要，自动刷新还没做。人也可以手动触发唤醒。装完后用 `tlx hook status` 自检。

### 4.8 管理员

管理员能创建和列出角色，批准或指派会话绑定，查看待批申请，修改管理密码，手动唤醒。管理员可以用现有角色发信；独立的审计日志和系统通知还没做，见第 10 节。

管理员操作需要密码，密码不存明文。agent 不应该能自己完成绑定。

人自己要看某个角色的信箱时怎么授权，还没定。先做管理员代读，还是给终端绑一个临时会话，是第 10 节的问题。

### 4.9 可观测

发件人能在已发送里看到每个收件人的投递状态、已读时间和回执时间。已读回执自动记录，回执由收件人主动给。

人能查看角色、绑定关系和待批申请。独立的审计日志和管理员代读还没做，见第 10 节。

### 4.10 通讯录

角色就是账号，也是通讯录的条目。agent 可以列出本机已有的角色和地址，知道该写给谁。人可以给角色加显示名。

邮件列表（一个地址对应一组收件人）之后再做，地址模型要留出位置。

## 5. 行为保证

- 信一旦收下就不会因为收件方没开窗口而丢失。
- 同一封信重复发送不会在收件箱里出现两份。
- 信的内容在收下之后不再改变；已读、回执、认领都是附加状态。
- 发出去的信保留在已发送里，收件人的投递、已读和回执状态对发件人可见。
- 通知不打断正在干活的 agent，默认只在启动时出现。
- 一个角色同时只有一个会话在代表它。
- 正文只当数据，不能靠正文让收件方执行动作。
- 过期的信不删除，仍然可以阅读，只是不再唤醒、不再计入角标。
- 索引是派生数据，删掉或损坏不影响邮件，可以从 spool 重建。

## 6. 失败时的表现

- 收件方长期不开会话：信一直等着，下次启动能看到角标，收件箱文件也能看到。
- 信过期：仍然可以读，只是不再提醒。
- 唤醒失败：重试若干次，仍失败就写进运行记录，`tlx doctor` 显示，信不动。
- 角色未绑定会话：信收下，不唤醒，等绑定。
- 会话被改绑：旧会话失去身份，未读跟着角色走。
- 管理员密码丢失：需要一条重置路径，具体方式未定。
- Telex 服务不可用：命令直接报错，不静默成功，也不假装信已经发出。

## 7. 安全边界

正文永远是数据。信的类型、收件人、动作参数都来自结构化字段，不能由正文决定。收件人只能来自信封里的收件人列表。

密送地址不会泄露给其他收件人。信的内容不可变，方便事后核对。

Telex 假设同一台机器上的用户和进程彼此不是敌人。它能防误操作和角色串用，也能靠已发送和 marker 事后核对，但防不住一个已经拿到本机账户权限的进程。需要更强隔离时，只能换独立账户或者上沙箱，不在本设计范围内。

## 8. 非目标

不做真实 SMTP，不注册域名，不跨机器，不做多租户，不做实时聊天，不做群组地址和邮件列表（之后再做），不做附件、草稿、归档、垃圾箱和全文搜索（P2 再看），不删除信，不把 MCP 当通知通道，不用模型判断一封信是不是攻击。

## 9. 里程碑

P0 和 P0.5 是原型，验证了本地收发、启动角标和唤醒命令。P1 做角色、会话绑定、管理员批准和常驻服务，让多 harness 真正能用。P2 做人类收件箱界面、附件、更深的 harness 适配。P3 做消息签名和回复预算。

## 10. 未决

- 人自己读某个角色的信箱怎么授权。管理员代读、普通用户身份和审计日志要不要做，后面再定。
- 角色删除或改名时，已有的信、未读和绑定怎么处理。
- 邮件列表的地址格式和展开规则，之后单独设计。
- 已读回执能不能关掉，还是默认全开。
- 人类收件箱界面在 P2 是否真的要做。
